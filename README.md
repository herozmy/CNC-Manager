# CNC-Manager v2

面向数控加工场景的程序台账系统，按“图纸 → 工序 → 程序 → 版本”组织 NC 文件，支持手机、平板和桌面浏览器访问。Go 服务内嵌 React 前端，业务数据使用 SQLite 保存。

源码分支为 `v2`，源码基线标签为 `v2`。应用构建版本以根目录 [VERSION](VERSION) 为准；可从 [Releases](https://github.com/herozmy/CNC-Manager/releases) 下载 Linux amd64 二进制及 SHA-256 校验清单。

## 主要功能

- **机台管理**：在“机台”页面新增、编辑、停用及重新启用机台，维护编号、名称、控制系统和备注。支持按编号、名称、控制系统和启停状态搜索；管理员还可按所属账号筛选、为启用账号新增机台，普通账号仅管理自己的机台。机台归属创建后固定，同一账号内编号唯一。打开机台可查看关联图纸、工序、程序及当前版本，继续按图纸、工序或程序信息搜索，直接进入图纸或程序详情。
- **工序机台**：新增或编辑工序时选择、更换或解除机台关联，详情显示编号和名称。可在工序表单内新增机台并选中，同一账号的其他工序可复用；列表按图纸所属账号限定，待分配图纸需先分配账号才能新增机台。停用只阻止新的关联，已有工序可保留原机台或解除关联；改名、停用和启用均保留程序版本、NC 文件、历史刀具表及机台刀库。
- **图纸与工序**：维护图纸号、类型、材料、价格、备注，以及装夹方式、分中方式和 X/Y/Z 坐标；支持搜索和删除确认。图纸价格以人民币元填写，可留空，支持零及最多两位小数，范围 0～999999999.99 元；在图纸详情查看和编辑。
- **NC 程序与版本**：在程序详情编辑程序号、名称、数控系统和备注，保存时检查修订号，冲突保留草稿并可确认载入最新信息；保留原有 NC 文件、版本历史和刀具表；上传、查看、下载文件，保留版本历史，选择当前版本并比较版本差异。
- **在线编辑**：行号、语法高亮、查找替换、跳转；支持另存新版本及覆盖冲突检查，处理 UTF-8 / GBK 编码。
- **版本刀具表**：维护刀具号、名称与刀补，支持从 NC 内容识别、手动增删和排序，每个版本独立保存。
- **账号管理**：仅设管理员和普通账号两种身份。普通账号可查看、下载、新建、编辑和删除自己的数据；管理员可管理全部数据、账号和密码重置。
- **操作日志**：管理员按操作者、时间、动作、对象类型及结果筛选记录；保留操作时的身份、数据归属与对象名称，业务写入与成功日志同事务提交。下载记录表示服务端开始处理请求，不表示客户端已完整保存文件。
- **备份与恢复**：管理员创建整站 ZIP，保存在服务器并列出；按需下载、确认删除，导入前检查并自动保存恢复副本。

## 从源码运行

需要 Go 1.27.1 或更高版本，以及 Node.js 24 和 npm。以下命令适用于 macOS / Linux 终端；生成当前系统和架构的程序。

```bash
git clone --branch v2 --single-branch https://github.com/herozmy/CNC-Manager.git CNC-Manager-v2
cd CNC-Manager-v2
npm --prefix frontend ci
npm --prefix frontend run build
mkdir -p .local/bin
(cd backend && go build \
  -ldflags "-X main.version=$(tr -d '[:space:]' < ../VERSION)" \
  -o ../.local/bin/cnc-manager ./cmd/server)
CNC_ADDR=127.0.0.1:8080 CNC_DATA_DIR=./data ./.local/bin/cnc-manager
```

打开 [http://127.0.0.1:8080](http://127.0.0.1:8080)，首次访问按页面提示创建管理员。浏览器必须能连接运行服务的电脑；局域网部署时可将监听地址设为 `0.0.0.0:8080`，其他设备通过服务器地址访问。

## Linux 构建

在源码根目录执行：

```bash
bash scripts/build.sh
```

生成 Linux amd64 单文件程序 `.local/release/cnc-manager`。前端和密码重置功能均已内置，运行时不需要 Node.js 或 Python。使用 `cnc-manager --version` 查看版本。

## Docker 部署

镜像内嵌前端，以 UID/GID `1000:1000` 运行，数据统一保存到 `/data`。推荐使用 Docker Compose 和命名卷。先从当前源码构建并启动：

```bash
docker compose -f compose.yaml -f compose.build.yaml up -d --build
docker compose ps
docker compose logs --tail=100 cnc-manager
```

通过服务器的 `8080` 端口访问。已有服务占用此端口时，在命令前设置 `CNC_PORT=8081`；只允许本机反向代理访问时设置 `CNC_BIND_IP=127.0.0.1`。镜像发布后可使用 `docker compose pull && docker compose up -d` 更新；默认使用 `herozmy/cnc-manager:latest`，`latest` 和 `v2` 均指向 v2 最新版，用 `CNC_IMAGE=herozmy/cnc-manager:v<版本号>` 固定版本。继续运行 v1 时应固定已有的 `v1.x.x` 标签。

更新前在管理员页面创建并下载备份，更新时复用原数据卷。`docker compose down` 保留数据卷，`down -v` 会删除数据。使用绑定目录代替命名卷时，先创建目录并赋予 UID/GID `1000:1000` 写权限。每个数据目录只运行一个服务实例。旧版数据需按“从 v1 迁移”操作，不直接复用旧版容器的数据目录。

需要在另一台 Linux 主机构建和推送时，配置本机 `.local/docker-remote.env`：

```bash
CNC_DOCKER_HOST=your-ssh-alias
CNC_DOCKER_WORK_DIR=/path/to/build-work
CNC_DOCKER_IMAGE=herozmy/cnc-manager
```

完成本机验证后执行 `bash scripts/docker-remote.sh build`。远端需要 Docker Engine、Buildx、rsync 和 Python 3。脚本只导出源码到远端工作目录的独立子目录，构建 Linux amd64 镜像并运行临时容器，验证健康检查、NC 上传下载、备份、容器重建后的账号与文件持久化，测试结束清理临时容器和数据卷，不自动切换现有服务或推送。发布审核通过后执行 `bash scripts/docker-remote.sh push`，从同一构建目录推送 `v<版本号>`、`v2` 和 `latest`，检查三者摘要一致，并拉取 `latest` 重新验证；已存在的版本标签仅允许复用完全相同的镜像，不覆盖其他内容。Docker 仓库登录在远端通过 `docker login` 完成。

## 配置

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `CNC_ADDR` | `127.0.0.1:8080` | 监听地址；Docker 镜像默认 `0.0.0.0:8080` |
| `CNC_DATA_DIR` | `./data` | 数据目录，运行账号需有写权限 |
| `CNC_MAX_UPLOAD_MB` | `64` | 单个 NC 文件上传上限，范围 1～1024 MB |
| `CNC_SESSION_HOURS` | `168` | 登录会话有效时长，范围 1～8760 小时 |

`GET /api/meta` 可查看正在运行的程序版本。

数据目录包含 `cnc.db`（数据库）、`nc/`（加密 NC 文件）、`nc.key`（文件解密密钥）和 `backups/`（备份）。整体迁移时应停服后复制完整目录，保留原密钥和访问权限。

## 使用流程

1. 管理员在“我的 → 账号管理”创建账号。管理员创建图纸时选择所属账号，默认选择自己；普通账号创建的图纸自动归自己所有；在图纸下添加工序，填写装夹和坐标等信息。
2. 在工序下创建程序，进入程序详情上传 NC 文件。
3. 查看版本和刀具表，按需编辑内容、维护刀补或选择当前版本。
4. 下载所需 NC 文件；加工前核对版本、刀具及机床参数。

NC 刀具识别和语法高亮用于整理与查看，不提供加工仿真或机床安全校验。当前为联网使用的响应式网页，尚不支持离线编辑和机床直连传输。管理员可查看全部数据，并在总览按账号筛选。普通账号的列表、搜索、详情、版本和文件接口均按个人归属校验；停用账号或修改身份后撤销该账号的会话。

已登录页面遇到短暂断网或服务器故障时，会保留当前打开的表单、待上传文件和说明，并提示重新连接；恢复网络后可重试。未提交内容仅保存在当前页面，刷新或退出前应先恢复连接并保存。服务器确认会话失效后，仍会退出登录并清除该账号的页面草稿。

## 备份与恢复

在“我的 → 备份与迁移”操作：

1. 点击“创建备份”。完成后 ZIP 保存在服务器，页面刷新列表，不自动下载。
2. 在“可恢复备份”中点击对应条目的“下载”，并在设备下载记录中确认保存；删除服务器备份需再次确认。
3. 选择“导入备份”，上传 v1 或 v2 整站 ZIP 并检查预览。v1 备份自动转换为当前 v2 数据；v2 备份要求数据库结构兼容。确认覆盖后导入。
4. 导入前系统自动备份目标数据。导入完成后使用备份中的账号和密码重新登录。

ZIP 包含账号、数据归属、操作日志、已保存的业务数据、NC 文件及密钥；不包含有效登录会话、未保存编辑或其他历史备份。导入会覆盖目标服务器的账号和业务数据。备份包未额外加密，请妥善保管。

网页备份上限为 ZIP 512 MB、解压后 2 GB、100,000 个 NC 文件。超出范围时采用停服复制完整数据目录的方式迁移。

v2.0.2 增加图纸价格字段，首次启动会自动升级数据库，原图纸价格为空。升级前完整备份数据；旧版 ZIP 需先用匹配版本恢复，再升级程序，新版 ZIP 包含价格。不将升级后的数据库直接交给旧版程序使用。

机台管理新增启停字段，首次启动时已有机台默认启用，原账号、关联和业务数据保留。升级前完整备份数据；升级前的 v2 ZIP 仍需先用匹配结构的旧程序恢复，再启动新程序升级。v1 网页导入继续转换到当前结构。

## 从 v1 迁移

网页支持直接导入 v1 程序导出的整站 ZIP，无需先执行命令行工具。在 v1 的备份功能中创建并下载 ZIP，然后由 v2 管理员在“我的 → 备份与迁移 → 导入备份”上传并检查。页面展示账号、图纸、工序、版本、刀具和 NC 数量，以及账号身份、数据归属和未导入项。检查只在临时目录中转换，确认覆盖后才导入；导入前自动保存当前 v2 的恢复副本。迁移后使用原 v1 账号和密码登录。

支持的 v1 ZIP 包含格式为 `1` 的 `manifest.json`、`data/cnccool.db` 和对应的 `data/nc/` 文件。缺失或损坏的 NC、旧数据库结构、异常路径或混合格式会拒绝导入，当前数据保留。仅接受整站 ZIP，不接受单独数据库或普通 NC 压缩包；网页上限仍为 ZIP 512 MB、解压后 2 GB、100,000 个 NC 文件。

兼容 v1 保留的 `.nc`、`.NC`、`.txt`、`.tap` 等程序文件后缀，迁移后保留原下载文件名。

超出网页范围或需要先转换独立数据目录时，可使用 `migrate-v1`。Docker 镜像内置该命令，也可从 v2 源码单独编译。在实际执行迁移的 macOS / Linux 主机上运行：

```bash
mkdir -p .local/bin
(cd backend && go build -o ../.local/bin/migrate-v1 ./cmd/migrate-v1)
./.local/bin/migrate-v1 -from /path/to/v1-copy -to /path/to/new-v2-data
```

使用 Docker 时无需在宿主机安装 Go。先构建包含迁移工具的镜像，再将 v1 副本只读挂载，将新的空目录作为目标。以下目录替换为实际绝对路径，目标不要使用正在运行的 v2 数据目录：

```bash
docker build -t cnc-manager:migration .
mkdir -p /path/to/new-v2-data
sudo chown 1000:1000 /path/to/new-v2-data
docker run --rm --network none --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --entrypoint migrate-v1 \
  --mount type=bind,src=/path/to/v1-copy,dst=/v1,readonly \
  --mount type=bind,src=/path/to/new-v2-data,dst=/v2 \
  cnc-manager:migration -from /v1 -to /v2
```

v1 副本须允许容器 UID/GID `1000:1000` 读取。迁移容器不启动网页服务，也不开放端口；失败时保留原空挂载目录并清理本次生成的内容，修正源数据后可重试。发布了包含迁移工具的新镜像后，可先拉取该固定版本镜像，再替换上述 `cnc-manager:migration`，无需重新编译；较早的镜像没有此命令。

先停止 v1 并备份完整数据目录，使用备份副本迁移。源目录需包含 `cnccool.db` 和对应的 `nc/`；旧库须已升级至结构迁移 `0010_machine_tool_magazine`。目标目录必须不存在或完全为空，已初始化的 v2 目录也不能作为目标。工具只读旧库，保留主键、业务字段、版本关联和刀具表，校验 NC 内容并用新生成的 `nc.key` 重新加密。缺失或损坏的被引用 NC 会使整次迁移取消，不生成可用的半份数据库。

迁移后使用原账号和密码重新登录，旧会话不导入；v1 账号全部成为管理员。图纸、机台和刀具进入“待分配”范围，仅管理员可见；分配图纸前需处理其机台、刀具关联，参见下节。未被版本引用的 NC 文件和旧登录会话不导入，工具会报告数量；v1 的 `app_setting` 扩展配置也不导入。完整备份新目录，尤其保留 `nc.key`。

验证新目录后，可停服备份现有 v2，再将新目录绑定到容器 `/data`，赋予 UID/GID `1000:1000` 写权限后启动。也可先用独立 v2 实例打开转换后的目录，导出 v2 整站 ZIP，再通过目标 v2 的网页检查和覆盖导入；这会替换目标账号及业务数据。不要把 v1 数据目录直接挂到 v2 容器，也不要同时运行两个服务访问同一数据目录。

## 个人数据归属升级

首次运行新版本源码时自动迁移数据库并撤销旧会话。升级前的图纸、机台和刀具保留在“待分配”范围，仅管理员可见；已有普通账号可直接登录并管理自己的新数据。旧角色下的共享数据不会自动分给任何个人，管理员需确认后分配。图纸号、机台编码和刀具编号在同一账号内唯一，不同账号可使用相同编号；旧角色下的同号记录会完整保留。

管理员在待分配图纸详情中选择账号并确认分配，其工序、程序、版本和刀具表继承图纸归属。图纸关联了其他归属的机台或刀具时会拒绝分配，须先解除这些关联。同一账号已有相同图纸号时也会拒绝分配，原数据不变。已分配图纸暂不支持转移到其他账号；更换账号身份不改变数据归属。

恢复要求数据库结构相同。升级前的 ZIP 先用匹配版本恢复，再升级；不要将升级后的数据库交给旧版程序。恢复前的完整回退副本保留恢复前历史，恢复后日志显示备份中的历史和新事件。历史日志保留原角色快照，缺失信息显示为未知。

## 忘记密码

从 `v2.0.1` 起，服务器管理员直接使用主程序的 `reset-password` 子命令：

```bash
sudo ./cnc-manager reset-password \
  --data-dir /opt/cnc-manager-v2/data \
  --service cnc-manager-v2.service
```

默认数据目录为 `/opt/cnc-manager-v2/data`（可通过 `CNC_DATA_DIR` 或 `--data-dir` 修改），默认服务为 `cnc-manager-v2.service`。服务必须显式配置相同的绝对路径 `CNC_DATA_DIR`；工具会核对目录与服务的对应关系。

只有一个启用账号时自动选择，多个账号时按编号选择；也可增加 `--user admin` 指定登录用户名。交互输入两次新密码（8～128 个字符），输入不显示，Ctrl+C 可取消；远程使用 `ssh -t` 分配终端。工具先停服，将完整数据复制到数据目录同级的 `backups/pre-password-reset-*/data/`，再事务修改密码并撤销该账号全部旧登录，最后恢复原本运行的服务。其他账号、业务数据和密钥保留。

```bash
./cnc-manager reset-password --help
./cnc-manager reset-password --data-dir /path/to/data --list
./cnc-manager reset-password --data-dir /path/to/offline/data --no-service
```

`--list` 只列出账号。`--no-service` 只用于已停止服务的离线数据目录，需由调用方先确认所有写入进程已停止；新版本有数据目录占用检查，旧版本不具备此检查。

备份或数据库操作失败不会提交密码变更，并尝试恢复服务；若提示“密码已重置，但服务恢复失败”，请检查服务状态后使用新密码登录。此功能依赖服务器文件访问/管理权限，无公开 HTTP 密码重置入口。

## 项目结构与检查

- `backend/`：Go 服务、接口、数据库、NC 解析与存储。
- `frontend/`：React + TypeScript 界面。
- `scripts/`：构建和服务器维护工具。
- `Dockerfile`：容器构建配置。

```bash
(cd frontend && npm ci && npm run typecheck && npm test && npm run lint && npm run build)
(cd backend && go vet ./... && go test ./...)
```
